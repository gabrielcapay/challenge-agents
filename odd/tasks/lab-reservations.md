# Plan de trabajo: reservas del laboratorio

## Objetivo
Construir una API local pequeña y reproducible con Spring Boot, Java y SQLite para consultar disponibilidad, reservar y cancelar equipos sin perder el historial. Este plan se basó en la consigna del Challenge-Agents. La entrega será un repositorio que permita revisar tanto el producto como el trabajo realizado con el agente de programación.

## Alcance y decisiones vigentes
- Inventario fijo y precargado: `MIC-01` y `MIC-02` (microscopios digitales), `OSC-01` (osciloscopio), `MUL-01` (multímetro), `FUE-01` (fuente de alimentación). Cada ID es una unidad física; no hay administración del inventario.
- Reservas identificables de una unidad con solicitante **ficticio**, inicio, fin y estado. Cancelar conserva ID y datos y libera el intervalo. Persistir activas y canceladas después de reiniciar la aplicación sin borrar la base.
- Validar ID conocido, solicitante no vacío ni solo espacios, fecha/hora válida e inicio estrictamente anterior al fin. Solo las activas bloquean; rechazar superposición de la misma unidad, permitir horarios consecutivos y simultaneidad en unidades distintas. Disponibilidad y creación aplican idénticas reglas.
- Documentar antes de implementar formato de fechas, zona horaria, fechas pasadas y límites de duración o anticipación (o ausencia de ellos). Propuesta a especificar: intervalos semiabiertos `[inicio, fin)` y fechas ISO 8601 con desplazamiento explícito; no afirmar que ya están implementados.
- Fuera de alcance: autenticación y roles reales, notificaciones, pagos, integraciones externas, despliegue obligatorio, interfaz gráfica compleja, concurrencia distribuida y escalabilidad de producción.
- El usuario eligió Spring Boot + SQLite y solicitó documentación en español (plan, especificación y README; código e identificadores pueden conservar nombres técnicos). Java 21 y Maven 3.9.12 están disponibles; todavía no se verificaron dependencias, configuración SQLite ni pruebas. La API y las pruebas deberán ejecutarse sin la cuenta del modelo. Usar un harness de agente existente, no crear otro; no se exige MCP, memoria externa, varios agentes ni servicios pagos.
- Trabajar en una rama de la funcionalidad, con un solo escritor a la vez. No publicar ni enviar el repositorio sin decisión del usuario. Estrategia inicial ante cambios grandes: consultar antes de entregar un bloque difícil de revisar. Estimación orientativa de líneas redactadas: especificación ~170, infraestructura ~250, reglas y pruebas ~350, evidencia/README ~200; no recortar pruebas ni documentación para ajustarse a esa estimación.
